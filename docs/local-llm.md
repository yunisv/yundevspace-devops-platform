# Локальный LLM (Ollama) для AI-агентов

`docs/ai-agents-roadmap.md` требует LLM, вызываемый из n8n. Раз diff'ы и
находки безопасности — чувствительные данные, используем локальную модель
через [Ollama](https://ollama.com) вместо стороннего SaaS API — данные не
покидают сервер. Ollama разворачивается как ещё один сервис в
`devops_edge` (`docker-compose.ollama.yml`), n8n стучится в неё напрямую по
имени контейнера (`http://ollama:11434`) — без Traefik-роута и без входа
через VPN, наружу это не публикуется вообще.

## 0. Реальный риск: конкуренция за ресурсы

Уже задействованный стек (GitLab + Keycloak + Plane + DefectDojo +
мониторинг + n8n) по таблице в `architecture.md` сам по себе рассчитан на
12-16 vCPU / 28-32 GB RAM. Инференс локальной модели — это дополнительная,
а не "бесплатная" нагрузка, особенно без GPU (на обычных Hetzner
CPU-инстансах его нет). Поэтому размер модели надо выбирать не "по
рекомендациям в интернете", а по тому, что реально свободно на этом
сервере сверх уже работающего стека.

Проверить перед деплоем:

```bash
echo '--- CPU ---'
nproc
echo '--- RAM (свободно/доступно) ---'
free -h
echo '--- Диск ---'
df -h /
```

Смотреть в `free -h` на колонку **available** (не `free`) — это то, что
реально можно отдать под ещё один процесс с учётом кэша страниц, который
ядро отдаст при необходимости.

## 1. Выбор модели по свободной RAM

Все варианты — [Qwen2.5-Instruct](https://ollama.com/library/qwen2.5) в
q4_K_M-квантовании: сильнее конкурентов в структурированном JSON-выводе
(критично — n8n парсит ответ модели как JSON) и заметно лучше остальных
в этом размерном классе работает с русским языком, что пригодится, когда
дойдём до постмортемов/задач в Plane (пункты 4-5 роадмапа), где вывод
модели читают люди.

| Available RAM (`free -h`, колонка available) | Модель | `OLLAMA_MODEL` | `OLLAMA_MEM_LIMIT` | `OLLAMA_CPU_LIMIT` | Место на диске |
|---|---|---|---|---|---|
| < 4 GB | **не деплоить сюда** — см. раздел 4 | — | — | — | — |
| 4-8 GB | Qwen2.5 3B | `qwen2.5:3b-instruct-q4_K_M` | `4g` | `2` | ~2 GB |
| 8-16 GB | Qwen2.5 7B | `qwen2.5:7b-instruct-q4_K_M` | `8g` | `4` | ~4.5 GB |
| 16+ GB | Qwen2.5 14B | `qwen2.5:14b-instruct-q4_K_M` | `12g` | `6` | ~9 GB |

Меньшая модель (3B) заметно чаще ошибается в структуре JSON и в
приоритизации находок — если сервер тянет только этот вариант, стоит
рассмотреть раздел 4 вместо того, чтобы мириться с низким качеством
вердиктов на всех 5 пунктах роадмапа сразу.

## 2. Деплой

Прописать в `.env` (значения — из строки выбранного тира выше):

```bash
OLLAMA_MODEL=qwen2.5:7b-instruct-q4_K_M
OLLAMA_MEM_LIMIT=8g
OLLAMA_CPU_LIMIT=4
```

Поднять и скачать модель:

```bash
docker compose -f docker-compose.yml -f docker-compose.gitlab.yml \
  -f docker-compose.monitoring.yml -f docker-compose.automation.yml \
  -f docker-compose.dashboard.yml -f docker-compose.ollama.yml \
  --profile runner up -d ollama

docker exec -it devops-platform-ollama-1 ollama pull qwen2.5:7b-instruct-q4_K_M
```

(Подставить свою модель, если тир другой — `pull` качает по имени из
`OLLAMA_MODEL`, вручную, один раз; при рестарте контейнера модель уже
лежит в volume `ollama-data`, повторно качать не нужно.)

## 3. Проверить

`docker-compose.ollama.yml` намеренно не пробрасывает 11434 на хост (см.
раздел 0) — поэтому `curl http://localhost:11434` с самого сервера ничего
не найдёт, запрос никуда не долетит и упадёт молча. Проверять через
встроенный CLI — он обращается к серверу Ollama изнутри контейнера, порт
наружу для этого не нужен:

```bash
docker exec -it devops-platform-ollama-1 ollama run qwen2.5:7b-instruct-q4_K_M "Ответь одним словом: работаешь?"
```

Первый запуск загружает модель в память (может занять минуту-полторы для
14B) — это нормально, не признак проблемы.

Из n8n workflow модель дергается иначе — HTTP Request node,
`POST http://ollama:11434/api/chat` (по имени сервиса внутри `devops_edge`,
n8n и Ollama сидят в одной docker-сети, порт на хосте им обоим не нужен).

## 4. Если свободной RAM не хватает

Не пытаться "втиснуть" модель через своп или урезание `mem_limit` ниже
таблицы — это either OOM-килл контейнера в разгар инференса, либо
деградация всего остального стека (Sidekiq в GitLab уже и так
чувствителен к нехватке памяти, см. `architecture.md`). Варианты:

- **Отдельный сервер под Ollama** — CX32/CPX31 в том же Hetzner-проекте,
  добавляется в сеть NetBird как обычный peer (как уже сделано для
  control plane), n8n стучится в него по адресу в VPN-подсети вместо
  `http://ollama:11434`. Изолирует нагрузку полностью, не требует
  апгрейда основного DevPlat.
- **Апгрейд DevPlat** — Hetzner позволяет resize сервера без пересоздания
  (с даунтаймом на несколько минут).
- **SaaS LLM API** вместо локальной модели — быстрее всего, но данные
  (diff, находки) уходят к третьей стороне; рассматривать только если
  для конкретных пунктов роадмапа это приемлемо (например, для пункта 5 —
  автоприоритизация задач по названию/описанию — обычно менее
  чувствительно, чем пункт 1 — ревью diff'ов кода).
