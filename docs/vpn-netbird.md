# Закрытый доступ: NetBird на отдельном сервере

Два сервера, у каждого своя роль:

```
клиент (ноутбук)
   │ NetBird (WireGuard-туннель поверх интернета)
   ▼
netbird-edge   — маленький сервер (2 vCPU/4GB хватает), публичный IP,
                 только control plane NetBird (management/signal/relay)
   │
   │ (координирует, сам трафик платформы через него НЕ идёт)
   ▼
DevPlat        — сервер платформы, тоже присоединён к сети NetBird как
                 обычный peer. GitLab/Keycloak/Grafana/... слушают ТОЛЬКО
                 на netbird-интерфейсе — публичных портов у платформы нет
                 вообще, ни одного.
```

Важное отличие от варианта с приватной сетью Hetzner: **приватная сеть
между серверами не нужна**. NetBird сам поднимает зашифрованный туннель
через интернет (WireGuard), P2P или через relay, если прямое соединение
не проходит из-за NAT. Поэтому edge-сервер и DevPlat не обязаны быть в
одном облаке/проекте/дата-центре — но раз оба уже в Hetzner, всё равно
удобнее держать их там.

## Зачем отдельный сервер, а не NetBird прямо на DevPlat

- **Control plane NetBird обязан быть публично доступен** (80/443/3478) —
  через него клиенты аутентифицируются и координируются. Если это тот же
  сервер, где стоит платформа, у платформы навсегда останутся открытые
  порты просто по факту совместного размещения.
- Отдельная машина = отдельный радиус поражения: если DevPlat
  скомпрометирован, не получают control plane VPN и наоборот.
- DevPlat при этом требований на открытые порты **не имеет вообще** — он
  просто ещё один peer в сети, все его сервисы висят на приватном
  netbird-адресе (`100.64.x.x`).

## Шаг 1. Купить сервер под NetBird

Hetzner Cloud → Add Server → CX22 (2 vCPU/4GB) достаточно, ~4-5 €/мес.
Можно в том же проекте, что DevPlat — общая приватная сеть для этого не
нужна, но так удобнее администрировать.

## Шаг 2. DNS для control plane

В зоне `2be.az` на Hetzner DNS — A-запись на **публичный** IP нового
сервера (не приватный, в отличие от записей самой платформы):

```
netbird    A    <публичный IP edge-сервера>
```

## Шаг 3. Установка control plane

На новом сервере:

```bash
export NETBIRD_DOMAIN=netbird.2be.az
curl -fsSL https://github.com/netbirdio/netbird/releases/latest/download/getting-started.sh | bash
```

Скрипт сам поднимает management/signal/relay (с версии 0.65 — единым
бинарём/контейнером) и получает TLS-сертификат на `netbird.2be.az`. Нужны
открытые 80/443/tcp и 3478/udp — это единственные публичные порты во всей
схеме, и они на **отдельном** сервере, не на платформе.

С версии 0.62 self-hosted NetBird имеет встроенное управление
пользователями — внешний IdP не обязателен. Но раз Keycloak у нас уже
поднят для остального (GitLab/Grafana/dashboard), лучше подключить его,
чтобы доступ выдавался и отзывался в одном месте — см. шаг 5.

Зайти в веб-дашборд NetBird (`https://netbird.2be.az`), создать первого
админа.

## Шаг 4. Присоединить DevPlat к сети как peer

На DevPlat (сервер платформы) — **не в Docker**, нативным пакетом:

```bash
curl -fsSL https://pkgs.netbird.io/install.sh | sh
```

В дашборде NetBird: Settings → Setup Keys → создать ключ (reusable,
без ограничения по количеству, если планируете так же подключать раннеры
и т.п. позже). Затем на DevPlat:

```bash
netbird up --setup-key <ключ_из_дашборда>
```

Проверить полученный адрес:

```bash
ip -4 -o addr show wt0
```

Обычно что-то вроде `100.64.0.2` — это и есть `BIND_ADDRESS` для `.env`
платформы.

## Шаг 5. Keycloak как IdP для NetBird (опционально, но рекомендую)

В NetBird Management Dashboard → Settings → Identity Provider → добавить
Keycloak как внешний OIDC-провайдер (realm `devops`, тот же, что и для
dashboard). Подробности:
https://docs.netbird.io/selfhosted/identity-providers/keycloak

Известная шероховатость: с Keycloak 26.x бывают проблемы совместимости
(netbirdio/netbird#4668) — если упрётесь, откатитесь на версию Keycloak
из этого репозитория (25.0, уже проверенная) или используйте встроенную
идентификацию NetBird вместо внешнего IdP.

## Шаг 6. Поставить клиент себе на ноутбук

Скачать с `https://netbird.ai/start` под вашу ОС, залогиниться (через
Keycloak, если подключили) или через встроенный логин NetBird.

## Проверка перед закрытием портов

```bash
ping 100.64.0.2                          # адрес DevPlat в сети NetBird
curl -I https://git.2be.az               # должно резолвиться на BIND_ADDRESS
                                          # и открываться через VPN
```

**Только после того как это заработало** — на DevPlat:

```bash
sudo ./scripts/harden.sh --dry-run
sudo ./scripts/harden.sh
```

## Шаг 7. Hetzner Cloud Firewall на DevPlat (deny-all inbound)

`ufw`/`harden.sh` работают на уровне ОС — но у Docker свои iptables-правила
(цепочка `DOCKER`), которые обрабатываются раньше `INPUT`, где живут
правила ufw. На практике это значит, что публикация порта контейнером
(`ports: ["8080:8080"]` на `0.0.0.0`) может остаться доступна снаружи
даже при включённом `ufw` — ровно так один раз и случилось при установке
DefectDojo (см. `adding-defectdojo-harbor.md`).

Hetzner Cloud Firewall работает на уровне гипервизора/сети, до того как
трафик вообще доходит до сервера — Docker его обойти не может в принципе.
Раз DevPlat не требует ни одного входящего порта вообще (NetBird
подключается как peer, исходящим соединением/hole-punching через
`netbird-edge`), тут можно поставить honest deny-all:

1. Hetzner Cloud Console → проект → **Firewalls** → **Create Firewall**.
2. **Inbound rules** — оставить пустым (ничего не разрешать явно).
3. **Outbound rules** — оставить дефолтный **Allow all**.
4. **Resources** → применить на сервер DevPlat.

Проверка сразу после применения — SSH через NetBird должен продолжать
работать, а публичный IP не должен отвечать вообще ни на что:

```bash
ssh devplat                                              # через NetBird — должен работать
curl -m 5 -sk https://<публичный IP DevPlat> -o /dev/null -w "%{http_code}\n"   # таймаут, не код
```

Это не замена `ufw`/`harden.sh`, а дополнительный слой поверх — оставить
оба: если один когда-то будет неверно настроен, второй всё ещё прикрывает.

## Если заперлись снаружи

Консоль Hetzner (Server → Console, работает в обход сети):

```bash
ufw disable
```

## Ограничение

Раз `automation.` (n8n) доступен только через NetBird, вебхуки от внешних
SaaS (github.com и т.п.) до него не дойдут. Внутри платформы — GitLab,
Plane, DefectDojo, Alertmanager — всё работает, они и так шлют вебхуки
внутри той же сети NetBird.
