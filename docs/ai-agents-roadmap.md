# Roadmap: AI-агенты в пайплайне

Цель — автоматическая оценка (риск/качество/приоритет) на этапах анализа
кода и прохождения пайплайна, без замены существующих SAST/DAST-сканеров:
LLM-агент читает уже структурированные результаты (diff, отчёты GitLab
SAST/Trivy/DefectDojo) и добавляет суждение поверх них — резюме,
приоритизацию, предложенный фикс, — там, где статическому анализатору не
хватает контекста.

## Точки интеграции (все — через n8n, без изменения самих CI-пайплайнов)

1. **Ревью Merge Request** — GitLab webhook (`Merge Request Hook`
   opened/updated) → n8n → получить diff через GitLab API → вызвать LLM →
   результат постится обратно как комментарий к MR через GitLab API.
2. **Приоритизация находок безопасности** — DefectDojo webhook (новая
   находка) → n8n → LLM оценивает эксплуатируемость/контекст (публичный
   ли эндпоинт, есть ли похожие закрытые находки) → обновляет severity/
   тэги в DefectDojo через API, при critical — создаёт issue в GitLab.
   **Реализовано и проверено вживую на продакшн-сервере** —
   `docs/ai-agent-defectdojo-triage.md`,
   `config/n8n/workflows/defectdojo-triage.json`. LLM — DeepSeek API
   (`api.deepseek.com`), не локальная модель: раньше была самохостнутая
   Ollama, но её сняли ради простоты (одна SaaS-зависимость вместо
   ресурсоёмкого локального инференса — для этого конкретного роадмапа
   утечка текста находок наружу сочли приемлемой).
3. **Gate пайплайна** — job в `.gitlab-ci.yml` отправляет summary (тесты,
   coverage, SAST quality gate, найденные CVE) в n8n → LLM возвращает
   pass/fail/needs-human-review → пайплайн опрашивает n8n (webhook-response
   node) и либо продолжает деплой, либо блокирует его (manual job/exit code).
4. **Постмортемы алертов** — Alertmanager → n8n → LLM собирает логи из
   Loki за инцидент и черновик post-mortem в GitLab wiki/issue.
5. **Автоприоритизация задач** — 2btask вебхук (`task.created`/
   `task.updated`, см. `server/INTEGRATION.md` в репозитории `yunisv/2btask`)
   → n8n → LLM оценивает приоритет/сложность по описанию и связанным MR
   → `PATCH /api/v1/tasks/{id}` проставляет priority в 2btask. Раньше этот
   пункт планировался под Plane (вебхуки на каждое событие в бесплатной
   Community-версии); после замены Plane на свой сервис (`docs/adding-2btask.md`)
   он ложится на собственный `/api/v1` — тот же принцип, свой контракт.

## Почему n8n, а не отдельный сервис агентов (пока)

На старте вся логика — это HTTP-node в n8n, вызывающий LLM API с нужным
промптом и парсящий JSON-ответ. Отдельный сервис (например, воркер на
Claude Agent SDK с собственными инструментами — чтение файлов из GitLab,
запуск повторных сканов) стоит выносить, когда понадобится:

- многошаговый агентный цикл (агент сам решает, какие ещё данные запросить);
- работа с большими диффами/репозиториями, не помещающимися в один запрос;
- переиспользование одной и той же агентной логики вне n8n (например, CLI для локальной проверки перед пушем).

В этот момент воркер добавляется как ещё один сервис в `devops_edge` и
n8n просто дергает его HTTP API вместо прямого вызова LLM — остальная
топология (вебхуки, куда постить результат) не меняется.

## Что нужно решить перед реализацией

- Какой LLM API использовать и куда должны уходить данные (diff/логи
  могут содержать чувствительный код — если это критично, приоритет —
  модель, которую можно развернуть локально/в VPC, а не публичный SaaS-API).
- Хранение секретов (API-ключ LLM) — через n8n credentials или вынести в Vault.
- Порог автоматического блокирования пайплайна LLM-агентом (рекомендуется
  начать в режиме "только советует", без права блокировать деплой, пока не накопится доверие к его вердиктам).
