# Доступ к платформе: сеть и закрытие портов

Платформенный сервер **не выставлен в интернет**. Обращения по публичному
IP нет ни у кого, включая администраторов.

## Топология

```
клиент (ноутбук)
   │ OpenVPN
   ▼
файрвол-машина  (публичный IP, терминирует VPN, выдаёт 172.16.1.0/24)
   │ приватная сеть Hetzner (vSwitch / private network)
   ▼
сервер платформы  (слушает ТОЛЬКО приватный IP)
   GitLab · Keycloak · Grafana · Prometheus · n8n · Homepage
```

VPN уже существует и живёт на отдельной машине-файрволе — отдельный
NetBird/WireGuard нам не нужен. Это и есть та самая изоляция VPN от
платформы: упал сервер платформы — VPN продолжает работать, скомпрометировали
платформу — не получили точку входа в сеть.

## Почему на сервере платформы нет открытых портов

Два независимых уровня:

1. **Сервисы биндятся только на приватный интерфейс.** В compose это
   `"${BIND_ADDRESS}:443:443"` — Docker вешает порт на конкретный адрес, а
   не на `0.0.0.0`. На публичном интерфейсе не слушает вообще ничего, ещё
   до всяких правил фаервола.
2. **ip-фильтр в Traefik** (`internal-only`) — отбивает запросы, чей адрес
   источника не из VPN-подсети, приватной сети или docker-сети. Защищает от
   ситуации, когда на приватную сеть попал кто-то посторонний.

Плюс `harden.sh` закрывает публичный интерфейс на уровне ufw — третий
уровень, на случай если кто-то однажды поменяет binding обратно на `0.0.0.0`.

Сертификаты выпускаются по DNS-01 через API Hetzner: Traefik ходит
**наружу** к Let's Encrypt и DNS API, входящие соединения для этого не
нужны. Поэтому порт 80 не открыт и не требуется.

## Настройка

### 1. Параметры сети в `.env`

```bash
BIND_ADDRESS=10.0.0.2        # приватный IP ЭТОГО сервера
VPN_SUBNET=172.16.1.0/24     # что раздаёт OpenVPN на файрволе
PRIVATE_SUBNET=10.0.0.0/16   # приватная сеть Hetzner
DOCKER_SUBNET=172.28.0.0/16  # внутренняя сеть контейнеров
```

Приватный IP смотрится так:

```bash
ip -4 -o addr show | awk '{print $2, $4}'
```

`install.sh` проверяет, что `BIND_ADDRESS` реально есть на машине, и
останавливается, если нет — иначе Traefik молча не поднялся бы.

### 2. DNS

Поддомены платформы (`git`, `sso`, `grafana`, `dash`, …) должны
резолвиться в **приватный IP** сервера. Это нормально: маршрут до
`10.0.0.0/16` есть только у тех, кто в VPN, для остальных запись
бесполезна. Проще всего wildcard `*.${BASE_DOMAIN} A 10.0.0.2`.

Если светить внутреннюю адресацию в публичном DNS не хочется — поднимите
split-horizon на файрволе (он раздаёт DNS VPN-клиентам), а в публичной зоне
оставьте только TXT-записи, нужные для выпуска сертификатов.

### 3. Маршруты на файрволе

В настройках OpenVPN-сервера на файрволе клиентам должен пушиться маршрут
до приватной сети, иначе они не увидят платформу:

```
push "route 10.0.0.0 255.255.0.0"
```

Плюс правило, разрешающее трафик из VPN-подсети в приватную сеть. Как
именно это настраивается — зависит от того, что за файрвол (в OPNsense и
pfSense это делается в веб-интерфейсе, в разделах OpenVPN и Firewall/Rules).

### 4. Закрыть публичный интерфейс

Только после того, как убедились, что через VPN всё открывается:

```bash
sudo ./scripts/harden.sh --dry-run
sudo ./scripts/harden.sh
```

## Если заперлись снаружи

Консоль Hetzner (Server → Console, это VNC в обход сети):

```bash
ufw disable
```

## Проверка

```bash
# с машины БЕЗ VPN — всё закрыто:
nc -z -w5 <публичный-IP> 443; echo $?   # ненулевой код
nc -z -w5 <публичный-IP> 22;  echo $?   # ненулевой код

# из VPN — работает:
curl -sS -o /dev/null -w '%{http_code}\n' https://git.${BASE_DOMAIN}
```

## Ограничение

Раз `automation.` (n8n) недоступен снаружи, вебхуки от **внешних** сервисов
(github.com и подобных) до него не дойдут. Внутри всё работает: GitLab,
Plane, DefectDojo и Alertmanager шлют вебхуки по той же приватной сети.
Если внешний вебхук всё же понадобится — пробрасывать его нужно через
файрвол на конкретный путь, а не открывать сервис целиком.
